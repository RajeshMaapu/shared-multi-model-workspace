# Credential ownership (Phase 2a)

Workshop never copies secrets into the repo or logs. Each engineer's
credentials follow a reference pattern:

## Devin
- Canonical key file: `~/.local/share/devin/credentials.toml` (static token).
- Profile link: `<WORKSHOP_HOME>/profiles/devin/data/devin/credentials.toml`
  → file symlink to the canonical file (created by `ProfileBuilder.devinProfile`).
- Session store is hardcoded at `~/.local/share/devin/cli`; the sandbox
  profile allows writes there (see ADR 0006).
- Login required: run `devin` once outside the sandbox to refresh
  `credentials.toml`; Workshop picks it up through the symlink.

## Kimi
- Profile dir: `<WORKSHOP_HOME>/profiles/kimi` with a **directory** symlink
  `credentials → ~/.kimi-code/credentials`. Never link the inner file —
  the refresh rotates `kimi-code.json` atomically inside the directory.
- `config.toml` is generated by Workshop (minimal managed:kimi-code profile;
  `api_key` is an empty placeholder — OAuth does the auth).
- Single-process rule: at most one Kimi harness process (ADR 0007) so only
  one writer can refresh the grant.
- Login required: `kimi acp` surfaces auth errors → adapter emits
  `.authRequired` → health shows "Login required". Fix by running
  `kimi --login` once in a terminal (writes into the linked dir).

## DeepSeek
- Key is a credential **reference**: `{file: ~/.kimi-code/config.toml,
  toml_path: [providers, deepseek, api_key]}`, read at request time by a
  targeted TOML scanner (`DeepSeekAdapter.readCredential`). It is never
  stored, logged, or echoed into errors.
- If the key rotates, edit `~/.kimi-code/config.toml`; no Workshop state to
  update.

## Capability tokens
- Daemon generates `<WORKSHOP_HOME>/profiles/<engineer>/token` (32 random
  bytes hex, mode 0600) on first start. `workshop-mcp` passes it via
  `--token-file` → `workshop.authenticate` binds the connection to
  `.engineer(id)` (ADR 0003 documents the same-uid trust boundary).
